# 네트워크 관측·판정 기준

MultiPingCheck는 측정 결과를 보여 주는 도구이며 **관측 하나만으로 장애 원인을 확정하지 않습니다.** 이 문서는 지연·손실·중간 Hop·상태 색상을 어떻게 해석하는지 설명합니다.

## 1. 최종 대상 우선

경로 중간 장비의 ICMP 응답은 실제 포워딩 성능과 다를 수 있습니다.

중간 Hop에서 손실이 높더라도 최종 대상이 안정적으로 응답하면 다음 가능성을 먼저 고려합니다.

- Control Plane ICMP rate limit
- ICMP 응답 우선순위 하향
- 방화벽/ACL 정책
- Traceroute 응답 제한
- 장비가 Transit traffic은 정상 포워딩하지만 자기 자신에 대한 ICMP는 제한

따라서 분석은 **최종 대상의 end-to-end 상태를 우선**하고 중간 Hop은 보조 증거로 사용합니다.

## 2. 기본 화면 상태

기본 화면의 대상별 상태는 다음 다섯 종류입니다.

| 상태 | 표시 | 운영 의미 |
|---|---|---|
| 정상 | 초록 | 최종 대상 관측이 안정적인 상태 |
| 주의 | 주황 | 손실 또는 지연 변동 등 확인할 이상 징후가 있는 상태 |
| 장애 | 빨강 | 높은 손실 또는 연속 응답 없음 등 심각한 상태 |
| 일시중지 | 회색 | 사용자가 해당 대상 측정을 중지한 상태 |
| 대기 | 회색 | 유효한 관측이 아직 없는 상태 |

UI의 상세 상태 기준에는 최종 대상 응답, 손실률, 지연 변동과 연속 timeout 등이 사용됩니다.

상태는 운영자의 1차 우선순위 판단을 돕기 위한 신호이며 SLA 판정이나 장애 원인 확정값이 아닙니다.

## 3. 지연시간

지연시간은 한 번의 RTT보다 추이가 중요합니다.

확인 포인트:

- 평상시 baseline 대비 증가했는가
- 특정 시간대에만 spike가 반복되는가
- 여러 대상이 동시에 증가하는가
- 한 대상만 증가하는가
- 손실과 함께 증가하는가
- 경로 변화와 같은 시각에 발생했는가

절대값만으로 장애를 판단하지 않습니다. 물리 거리, VPN, 무선 구간, 인터넷 경로에 따라 정상 RTT가 다르기 때문입니다.

## 4. 패킷 손실

Packet loss는 최종 대상과 중간 Hop을 분리해서 봅니다.

### 최종 대상 손실

최종 대상에서 지속적으로 발생하는 손실은 실제 서비스 품질 문제 가능성이 높습니다.

함께 확인할 항목:

- 손실 발생 시간
- 평균/최대 RTT
- 연속 timeout 여부
- 같은 네트워크의 다른 대상 상태
- 해당 시점의 장비/회선 로그

### 중간 Hop 손실

중간 Hop에서만 loss가 나타나고 뒤 Hop/최종 대상이 정상이라면 그 Hop 자체의 forwarding loss라고 단정하지 않습니다.

## 5. 지연 변동(Jitter)

이 프로그램의 `jitter_ms`는 **성공한 RTT 표본의 표준편차**입니다. [HopMetricTracker.snapshot](../app/core/metrics.py)은 유효 RTT가 2개 이상일 때 다음 값을 계산합니다.

```text
sqrt(sum((RTT - 평균 RTT)^2) / (유효 RTT 표본 수 - 1))
```

유효 RTT가 2개 미만이면 값은 `None`이며, 실패한 측정을 0 ms RTT로 넣지 않습니다. 전체 추적 값과 선택한 시간 범위의 값은 포함된 표본이 다를 수 있습니다.

이 값은 왕복 지연의 분산 정도를 비교하는 보조 지표입니다. 단방향 지연 변동, 연속 패킷 간 지연 차이 또는 RTP jitter를 직접 측정한 값은 아니므로 음성·영상 서비스의 품질 기준에 그대로 대입하지 않습니다. 변동이 반복적으로 크면 같은 시간대 서비스 증상과 다른 증거를 추가 확인합니다.

## 6. 여러 대상의 동시 이상

다중 대상 모니터링의 장점은 **문제가 한 대상인지 공통 구간인지** 비교할 수 있다는 점입니다.

예:

```text
Gateway A   정상
Gateway B   정상
Server A    장애
Server B    정상
```

이 경우 공통 로컬 구간 전체 장애보다 Server A 또는 그쪽 경로에 한정된 문제를 우선 의심할 수 있습니다.

반대로 여러 독립 대상이 같은 시각에 동시에 지연/손실을 보인다면 다음 공통 요소를 확인할 가치가 높습니다.

- 로컬 uplink
- WAN/VPN tunnel
- ISP 경로
- 공통 firewall/NAT
- 무선 접속 구간

이 역시 자동 확정이 아니라 **조사 범위를 좁히는 상관관계**입니다.

## 7. 시간 범위 비교

MultiPingCheck는 최근 범위와 측정 전체를 분리합니다.

최근 범위는 현재 장애를 빠르게 보는 용도이고, 측정 전체는 다음을 확인하는 데 유용합니다.

- 반복되는 특정 시간대 장애
- 장애 시작 시점
- 복구 시점
- 지연 baseline 변화
- 간헐적 packet loss 패턴

짧은 화면 범위에서 정상으로 보이더라도 과거 세션에 장애가 존재할 수 있으므로 장애 접수 시점과 그래프 시간을 맞춰 확인합니다.

## 8. 데이터가 부족한 경우

샘플 수가 적거나 중간에 프로그램이 일시중지되었다면 과도한 결론을 내리지 않습니다.

확인 항목:

- 유효 Sample 수
- 세션 시작/종료 시각
- Pause 구간
- Session Log 복구 경고
- 손상/skip된 row 유무

부분 손상 세션은 복구된 부분만 분석 가능한 것으로 봅니다.

## 9. Alert는 관측 규칙이다

고급 기능의 Alert는 손실·지연·Jitter·샘플 수·지속시간 등의 조건을 자동 확인합니다.

Alert가 발생했다는 사실은 다음 의미입니다.

> 설정한 관측 조건이 충족되었다.

다음 의미는 아닙니다.

> 네트워크 장애 원인이 자동으로 확정되었다.

Alert는 장애 분석의 시작점으로 사용합니다.

## 10. Field Verification 원칙

실제 네트워크 검증에서는 다음 순서를 권장합니다.

1. 정상 상태 baseline 확보
2. 2개 이상 독립 대상 동시 측정
3. 장애 신고 시간대와 그래프 시각 정렬
4. 최종 대상 손실/지연 확인
5. 다른 대상과 상관관계 확인
6. 필요 시 실제 장비 로그와 대조
7. 프로그램 관측값과 실제 서비스 증상을 함께 기록

실제 사내 IP나 로그 원문을 GitHub에 올리지 않습니다.
